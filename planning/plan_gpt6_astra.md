### 1. Разбор задачи

Организаторам нужна работающая диспетчерская система:

> Получить телеметрию → определить состояние транспорта относительно расписания → заранее спрогнозировать задержку → показать понятный алерт.

**ML-задача точно определена README.** Объект прогнозирования — пара `(tr_id, T)`. Для неё уже указано целевое плановое прибытие:

- `target_stop_id` — идентификатор записи расписания;
- `target_time_begin` — плановое время прибытия;
- `target_delay_s` — фактическое прибытие минус плановое, в секундах.

Это регрессия со знаком: отрицательное значение означает опережение. В submission нужна именно величина задержки, а не вероятность.

**Инженерная задача:** непрерывно принимать бинарный NDTP, связывать `unit_id` с `tr_id`, поддерживать историю, рассчитывать признаки, вызывать отдельный ML-сервис и обновлять dashboard.

**Распределение баллов по PDF:**

| Критерий | Максимум |
|---|---:|
| Точность ML | 6 |
| Горизонт и раннее предупреждение | 4 |
| Три работающих модуля и Docker | 6 |
| Dashboard | 6 |
| Производительность и надёжность | 4 |
| Питч | 10 |
| **Всего** | **36** |

ML даёт только 6 из 36 баллов. Поэтому улучшение модели не должно останавливать интеграцию.

За ML: score ≥0,70 даёт 6 баллов; 0,60–0,69 — 5; 0,50–0,59 — 4; 0,40–0,49 — 3. Заявленный в README score готового baseline — около 0,40; фактический результат нужно подтвердить платформой.

**Что означает горизонт 10–15 минут**

Для каждой точки:

```text
T — момент формирования прогноза
S — плановое прибытие на целевую остановку

600 < (S − T) ≤ 900 секунд
target = фактическое прибытие − S
```

Выбирается **первое плановое прибытие** в этом окне. Проверил: все train/test/validate points соответствуют этому правилу.

Это не «взять скорость через 15 минут» и не «предсказать задержку ровно в `T+15`».

Есть различие между формулировками документов: PDF говорит о времени до фактического события, README задаёт окно относительно **планового прибытия**. Реализуем точное правило README, а на demo показываем отдельно:

- время выпуска прогноза `T`;
- плановое прибытие `S`;
- горизонт `S−T`;
- прогноз задержки;
- ожидаемое фактическое прибытие `S + prediction`.

**Защита от leakage:**

1. Телеметрия для строки доступна только при `event_time ≤ T`.
2. Окна rolling заканчиваются в `T`; запрещены centered rolling и backward fill из будущего.
3. `target_delay_s`, `target_class`, `time_fact_begin` не попадают в признаки.
4. `cur_dev_s` разрешён README как известная на `T` подсказка.
5. Целевые координаты и будущее **плановое** расписание допустимы.
6. При временной проверке обучение использует только outcomes, уже наступившие к границе обучения.
7. В онлайн-системе учитывается ещё и фактическое время получения сообщения. Для офлайн-сабмита README явно задаёт доступность по `event_time`; проверку по `receive_time` делаем отдельным реалистичным сценарием.

**Главный контракт:** offline builder и backend вызывают одну функцию:


Она не читает labels или будущие факты. В offline источник `cur_dev_s` — разрешённая подсказка; online — причинная оценка прошедших прибытий. Источник и качество этой оценки записываются отдельно.

На старте достаточно памяти процесса для bounded history и SQLite/JSONL для прогнозов и метрик. Один backend worker, один владелец состояния. Kafka, Redis и отдельный feature store пока не нужны.

### 7. Работа с NDTP emulator

**Формат известен.** `ndtp/dataset` — распакованный OCI/Docker-образ, а не второй транспортный датасет.

Проверено:

- тег `ndtp-telemetry-emulator:1.0`;
- платформа `linux/amd64`;
- entrypoint `java -jar /app/app.jar`;
- API на `18080`;
- два имеющихся `.tar` идентичны.

**1. Запуск на машине с Docker:**

```bash
docker load -i dataset/ndtp-telemetry-emulator.tar

docker run --rm \
  --name ndtp-emu \
  -p 18080:18080 \
  --add-host=host.docker.internal:host-gateway \
  ndtp-telemetry-emulator:1.0
```

**2. Проверка API:**

```bash
curl -fsS http://localhost:18080/api/cells
curl -fsS http://localhost:18080/api/config
```

**3. Сначала поднять наш TCP listener на 9201, затем загрузить конфиг:**

```bash
curl -fsS -X POST http://localhost:18080/api/config \
  -H 'Content-Type: application/json' \
  -d '{
    "targetHost": "host.docker.internal",
    "targetPort": 9201,
    "units": [{
      "unitId": 664030,
      "intervalMs": 5000,
      "autoGenerate": true,
      "cells": []
    }]
  }'
```

В Compose `targetHost` будет именем backend-сервиса.

**4. Parser:**

```text
NPL: 15 байт
NPH: 10 байт
body: dataSize − 10 байт
общая длина кадра: 15 + dataSize
```

Все поля little-endian. CRC — CRC-16/Modbus по NPH и телу, с перестановкой байтов при записи в NPL.

- Handshake: service `0`, type `100`.
- Realtime: service `1`, type `101`.
- Навигация `G6CellNav00` идёт первой.
- Заголовок ячейки — type и number, затем payload; Nav00 payload — 26 байт.
- Координаты делятся на `1e7`, знаки берутся из битов.
- `peerAddress` соответствует `unit_id`, не `tr_id`.

TCP — поток байтов: один `read()` может вернуть часть кадра или несколько кадров. Нужны буфер, проверка длины и CRC.

У ячеек нет общей длины в заголовке. Неизвестный тип нельзя безопасно пропускать произвольным числом байтов. Для MVP достаточно декодировать первую Nav00 и игнорировать остаток уже выделенного кадра.

**5. Проверки parser:**

- handshake;
- один пакет;
- пакет частями;
- два пакета одним чтением;
- повреждённый CRC;
- переподключение с повторным handshake.

Эмулятор, по спецификации, сам переподключается и не требует полноценной обработки серверных ответов.

**6. Главный demo-риск:** эмулятор ставит текущее время, а расписание — январское. Его автогенерация не следует историческому маршруту.

Поэтому нужны два явно обозначенных режима:

- **Live NDTP:** демонстрирует реальный бинарный приём, parser, прогноз и обновление UI на согласованном демонстрационном расписании.
- **Historical replay:** воспроизводит настоящую траекторию и прогнозные точки с виртуальными часами, показывает раннее предупреждение и последующий outcome.

Для первого режима выбрать несколько плановых посещений, сдвинуть их на текущий demo-интервал, задать фиксированную географию Nav00 и явный mapping устройства к ТС. Источник расписания пометить как demo.

Для historical replay будущее событие раскрывается только при достижении его виртуального времени. Не выдавать ускоренное воспроизведение за ожидание 15 реальных минут.

### 8. Dashboard

Предлагаю **Streamlit + pydeck**.

Обновление через периодический fragment, например раз в 2 секунды. Streamlit поддерживает такой режим через `run_every`. [Документация](https://docs.streamlit.io/develop/api-reference/execution-flow/st.fragment)

**Один экран:**

- сверху: число ТС, активные риски, свежесть потока, p95 latency;
- слева: карта с ТС и целевыми остановками;
- справа: отсортированные карточки инцидентов;
- снизу: выбранное ТС — история скорости, прогноз, расписание.

Карточка должна за несколько секунд отвечать:

> Какое ТС? Где? Когда ожидается прибытие? На сколько опоздает? Почему система так считает? Что можно проверить диспетчеру?

Показывать:

```text
ТС 131672
Прогноз выпущен: 03:35
Плановое прибытие: 03:50
Горизонт: 15 минут
Ожидаемое отклонение: +...
Признак: длительный наблюдаемый простой
Качество данных: актуальные / устаревшие
```

Риск: зелёный/жёлтый/красный; серый — недостаточно данных. Опережение более 60 секунд отмечать отдельно.

Причины формулировать как **гипотезы, подкреплённые признаками**. Снижение скорости не доказывает пробку; без дверных данных нельзя утверждать длительную посадку.

Маршрутных геометрий в раздаче нет. Можно показать последовательность плановых посещений линиями, подписав её «плановая последовательность остановок». Не выдавать прямые отрезки за реальную дорожную трассу.


### 16. Риски

| № | Риск | Mitigation |
|---|---|---|
| 1 | Неверный target: классификация вместо секунд или physical stop вместо посещения | Зафиксировать формулу, ключи и единицы в schema |
| 2 | Утечка из `time_fact_begin`, общих периодов и синтетики | Whitelist признаков; не создавать labels из полного расписания; temporal audit; вопрос организаторам |
| 3 | Формальный horizon без раннего online-алерта | Логировать `T`, `S`, `generated_at`, источник часов; показать replay до outcome |
| 4 | Разные offline/online features, особенно `cur_dev_s` | Один feature engine; parity test; отдельная оценка online departure/arrival state |
| 5 | Ошибки NDTP и обрывы | Буфер TCP, CRC, fixtures, reconnect, bounded history |
| 6 | Неверный map matching и выдуманная маршрутная сеть | Простая последовательность плановых посещений; геозона + порядок + время; показывать неопределённость |
| 7 | Нет valid submission | Сразу сохранить готовый sample, проверить локально, загрузить заранее |
| 8 | Docker не работает или образ несовместим | Проверить сейчас; образ amd64; сборка на машине сдачи; startup smoke test |
| 9 | Поздняя интеграция | Mock-контур в первый час, реальный — в первый рабочий блок; Паша владелец integration |
| 10 | Переусложнение ML и потеря инженерных баллов | Ограничить набор экспериментов; freeze новых функций заранее; CPU baseline всегда доступен |
