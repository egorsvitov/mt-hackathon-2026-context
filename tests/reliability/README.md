# Тесты надёжности

Проверка критерия 5 («Производительность и надёжность») на поднятом `docker compose`:
отказы сервисов, мусор на входе, нагрузка, долгий прогон и несколько автобусов на маршруте.

## Запуск

```bash
docker compose up --build -d
# синтетика: к каждому из 13 ТС по 3 копии с интервалом 7 мин (52 ТС, 379 тыс. отметок)
python tests/reliability/make_multibus.py --data-dir ../dataset --out ../synthetic/multibus --clones 3
python tests/reliability/run_tests.py                          # все сценарии, ~25 мин
python tests/reliability/run_tests.py ml_outage throughput     # выбранные
```

Нужны `requests`, `aiohttp`, `pandas`; для `mixed_sources` — образ эмулятора
(`docker load -i ../dataset/ndtp-telemetry-emulator.tar`). Сценарии пересоздают backend с нужным
окружением (`REPLAY_AUTOSTART`, `REPLAY_SPEED`, синтетический датасет через `compose.synthetic.yml`)
и в конце возвращают его в режим по умолчанию. Результаты — `results/<сценарий>.json`.

Дополнительно проверено вручную:

* **Дашборд при падении backend** — красный баннер «Нет связи с сервером. Показано состояние на …; повтор каждые 2 с», карта и инциденты остаются; после старта backend дашборд сам продолжает работу.
* **Живой поток NDTP** (backend без replay, 3 ТС с расписанием, 75 с): ТС на карте «на связи», прогнозов нет — расписание на 06.01.2026, а поток идёт с текущей датой. Так и задумано: эмулятор шлёт синтетику, он проверяет приём и разбор NDTP; прогнозы показываются на воспроизведении исторического дня.
* **Эмулятор из профиля compose** (`docker compose --profile emulator up -d`, порт 18080, `targetHost: ndtp-parser`): кадры доходят до парсера, дашборд на 18090 работает рядом.

## Что найдено и что предлагаем

**Исправлено в ветке fix/reliability**

1. **Отметки «из будущего» замораживали ТС** (`VehicleTrack.add` и расписание прогнозов доверяли времени устройства). Теперь `pipeline.ingest` отбрасывает отметки новее часов системы больше чем на `MAX_FUTURE_SKEW_SEC` (в replay — часов воспроизведения) и считает их в `rejected_future`.
2. **Порты расходились с инструкциями.** Дашборд перенесён на 18090 (18080 — API эмулятора организаторов). Эмулятор добавлен в compose профилем `emulator`; в `ndtp-parser/README.md` — рабочая конфигурация (`targetHost: ndtp-parser`, `targetPort: 9201`, снаружи — 19201).

**Надёжность**

4. **Парсер: ресинхронизация.** После кадра с неверным CRC или завышенным размером выбрасывается весь заявленный объём. Предложение: ограничить `data_size` (кадр NDTP — десятки байт) и при ошибке сдвигаться на 1 байт к следующей сигнатуре.
5. **Нет буфера при недоступном backend.** Предложение: очередь с повтором в парсере (ограниченная по размеру).
6. **Состояние только в памяти.** Перезапуск backend сбрасывает инциденты и историю сверки, replay начинается заново с 08:30.

**Несколько автобусов на маршруте**

7. Прогнозы, инциденты и нагрузка — работают (см. `soak`, `throughput`). Но **map matching не видит новые ТС**: каталог привязан к 13 ТС и их рейсам 06.01 (`Matcher._candidates` ищет только среди рейсов этого `tr_id` и в их временных окнах), поэтому новые машины и любые другие даты идут сырым GPS без направления. И **дашборд считает каждое ТС маршрутом** («33 из 52 маршрутов на линии», «Маршрут ТС 122613 (копия 1)»): в данных нет номера маршрута. Для реальной работы нужна группировка ТС по маршруту — например, по `route_pattern_id` / `direction_id` каталога.
